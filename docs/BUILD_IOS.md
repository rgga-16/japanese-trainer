# Building the iOS app on Windows

You are on Windows 11 with no Mac and no Apple hardware, and have never used Xcode. Here's the hard
truth up front: **compiling and code-signing an iOS app requires macOS + Xcode.** There is no
supported way around this — Apple doesn't ship an iOS toolchain for Windows or Linux, and there's no
legitimate workaround (Hackintosh VMs violate Apple's EULA and are unreliable for CI). This guide
gives you three ways to get access to that toolchain without owning a Mac.

## The three routes

| | Cost | Interactive Xcode | Debug on your own iPhone | Ship to TestFlight | Best for |
| --- | --- | --- | --- | --- | --- |
| **A. A Mac you can sit at** | $0 (borrowed/friend's) or Mac hardware price | Yes | Yes (plug in via cable) | Yes | One-off builds, real debugging sessions |
| **B. GitHub Actions `macos-latest`** | Free tier minutes, then ~$0.08/min (macOS runners are billed at a 10x multiplier) | No | No | Yes (via exported IPA) | Automated/repeatable builds, no Mac ever |
| **C. Rented cloud Mac** (MacStadium, MacinCloud, AWS EC2 Mac, Scaleway Mac mini) | ~$20–50/mo or hourly | Yes (remote desktop) | No — can't plug your phone into a remote machine | Yes | Interactive debugging without owning hardware |

All three routes hit the same blocker first — read the next section before picking one.

## Universal prerequisites

- **Apple ID** — free, sign up at [appleid.apple.com](https://appleid.apple.com) if you don't have one.
- **Free Apple ID vs. paid Apple Developer Program:**
  - A free Apple ID lets Xcode sign a build for **on-device development only**, and that signature
    **expires after 7 days** — you have to reconnect and re-run to renew it. No TestFlight, no App Store.
  - The **Apple Developer Program** ($99/yr) is required for TestFlight distribution, App Store
    submission, and signing that doesn't expire weekly.
- **Project identifiers** (already set in this repo, you don't need to change them unless you're
  publishing under your own account with a different bundle id):
  - Bundle identifier: `com.rgeegallega.jlptn4trainer`
  - Deployment target: iOS 15.0
  - Device family: iPhone + iPad (`TARGETED_DEVICE_FAMILY = "1,2"`)
  - Marketing version / build number: `1.0` / `1`
  - Xcode scheme/target name: `App`

## The `Package.swift` backslash blocker (read this first)

Capacitor 8 uses **Swift Package Manager**, not CocoaPods — there is no `Podfile`, no `Pods/`
directory, and no `.xcworkspace` in this repo. You always open
[`ios/App/App.xcodeproj`](../ios/App/App.xcodeproj) directly, never a workspace. If a guide anywhere
tells you to run `pod install`, ignore it — it doesn't apply here.

Dependencies are wired in as a local Swift package at
[`ios/App/CapApp-SPM/Package.swift`](../ios/App/CapApp-SPM/Package.swift). That file was generated by
running `cap sync` **on this Windows machine**, and Node/Capacitor wrote the local package paths using
Windows backslashes:

```swift
        .package(name: "CapacitorApp", path: "..\..\..\node_modules\@capacitor\app"),
        .package(name: "CapacitorFilesystem", path: "..\..\..\node_modules\@capacitor\filesystem"),
        .package(name: "CapacitorShare", path: "..\..\..\node_modules\@capacitor\share"),
        .package(name: "CapacitorStatusBar", path: "..\..\..\node_modules\@capacitor\status-bar")
```

SPM on macOS parses `path:` as a POSIX path. A backslash isn't a separator there, so it can't resolve
these packages — the very first build step, package resolution, fails before any Swift or Objective-C
code even compiles.

**Fix (recommended): re-run sync on the Mac.** The file's header says:

```
// DO NOT MODIFY THIS FILE - managed by Capacitor CLI commands
```

That's not a suggestion to leave it broken — it means the *right* way to fix it is to let the
Capacitor CLI regenerate it, on a POSIX host, where it naturally writes forward slashes:

```bash
npm ci
npm run sync   # = npm run build:native && cap sync
```

Do this as the first step on the Mac (Route A), inside the CI job before `xcodebuild` (Route B), or
on the rented Mac (Route C). Every route below assumes this step happens on a real POSIX machine, not
on Windows.

**Fallback only:** if for some reason you can't run `cap sync` on a POSIX host, you can hand-edit the
four `path:` lines to forward slashes (`../../../node_modules/@capacitor/app`, etc.). This works, but
it's not durable — the next time anyone (including you, from Windows) runs `cap sync`, Capacitor
regenerates the file with backslashes again and silently reintroduces the blocker.

## Route A — a Mac you can sit at (borrowed, bought, or a friend's)

This is the most straightforward route if you have any access to physical Mac hardware, even
temporarily.

1. **Install Xcode** from the Mac App Store. It's a ~15 GB download — start it early, it's slow.
2. **Install the Command Line Tools** (usually prompted automatically on first Xcode launch, or run):
   ```bash
   xcode-select --install
   ```
3. **Install Node 22.x** (Vite 7 requires `^20.19.0 || >=22.12.0`) — via [nodejs.org](https://nodejs.org)
   or `brew install node@22`.
4. **Get the repo onto the Mac** (clone, or copy over from Windows) and install dependencies:
   ```bash
   npm ci
   ```
5. **Sync the native project** — this is also what regenerates `Package.swift` with correct
   forward-slash paths (see the blocker section above):
   ```bash
   npm run sync
   ```
6. **Open the project:**
   ```bash
   npx cap open ios
   ```
   or open [`ios/App/App.xcodeproj`](../ios/App/App.xcodeproj) directly from Finder/Xcode's Open dialog.
   Do **not** look for or open a `.xcworkspace` — there isn't one.
7. **Let Xcode resolve Swift packages.** On first open, Xcode shows a progress bar ("Resolving Package
   Graph") while it fetches `capacitor-swift-pm` 8.5.0 and links the four local plugin packages. This
   can take a few minutes on first run — let it finish before doing anything else.
8. **Set your signing team.** Select the `App` project in the navigator → the `App` target → **Signing
   & Capabilities** tab → check "Automatically manage signing" → pick your Team from the dropdown
   (your personal Apple ID team works for development). `DEVELOPMENT_TEAM` is intentionally unset in
   the committed project file, so this step is required on any machine.
9. **Run on the Simulator** — pick any iPhone/iPad simulator from the scheme device menu and hit Run
   (⌘R). No signing team is required for the simulator.
10. **Run on a physical iPhone** — plug it in via cable, select it as the run destination, hit Run.
    First launch will fail to open with an "Untrusted Developer" prompt on the phone — go to
    **Settings → General → VPN & Device Management**, find your certificate, and tap Trust. Re-launch
    from Xcode or the home screen.
11. **Archive for TestFlight/App Store** — **Product → Archive** (only enabled when a real device or
    "Any iOS Device" is selected as the destination, not a simulator). Once the archive finishes, the
    Organizer window opens — **Distribute App** to upload to App Store Connect, or export an IPA
    locally.

## Route B — GitHub Actions `macos-latest` (no Mac at all)

GitHub-hosted `macos-latest` runners give you a real, disposable macOS + Xcode environment per run.
Two workflows below: run (a) today with zero setup to prove the project compiles; add (b) later once
you're ready to sign and ship.

Save either as `.github/workflows/<name>.yml`.

### B1 — zero-secrets smoke build (Simulator, unsigned)

Proves the Xcode project resolves and compiles, with no certificates or secrets needed at all.

```yaml
name: ios-smoke-build

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

jobs:
  build:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: "22"

      - run: npm ci

      # Regenerates ios/App/CapApp-SPM/Package.swift with POSIX paths —
      # required because the committed copy has Windows backslashes.
      - run: npm run sync

      - name: Build for the Simulator (unsigned)
        run: |
          xcodebuild \
            -project ios/App/App.xcodeproj \
            -scheme App \
            -sdk iphonesimulator \
            -configuration Debug \
            CODE_SIGNING_ALLOWED=NO \
            build
```

Check `actions/checkout` and `actions/setup-node` are still pinned to their current major versions
when you add this — `v4` is correct as of this writing but confirm before relying on it long-term.

### B2 — full signed archive + IPA export

This needs an Apple Developer Program membership and a set of secrets pulled from your account. It
archives, exports a signed IPA, and uploads it as a workflow artifact (with an optional TestFlight
upload step at the end).

**Required repo secrets:**

| Secret | What it is | How to produce it |
| --- | --- | --- |
| `BUILD_CERTIFICATE_BASE64` | Your Apple Distribution (or Development) signing certificate, `.p12` format, base64-encoded | On any Mac with the cert installed: Keychain Access → find the certificate → right-click → Export → save as `.p12` with a password. If you don't have a Mac yet, you can generate a CSR with `openssl`, upload it in the Apple Developer portal under Certificates to get a `.cer`, then combine cert + private key into a `.p12` with `openssl pkcs12` — doing this without ever touching a Mac is fiddly; it's genuinely easier with even brief access to Route A or C to do this one-time setup. |
| `P12_PASSWORD` | The password you set when exporting the `.p12` above | Whatever you chose during export |
| `KEYCHAIN_PASSWORD` | An arbitrary password for the temporary CI keychain | Make one up, e.g. a random string — only used within the job |
| `PROVISIONING_PROFILE_BASE64` | The provisioning profile matching your cert + `com.rgeegallega.jlptn4trainer`, base64-encoded | Apple Developer portal → Profiles → create an App Store (or Ad Hoc/Development) profile for the bundle id, download the `.mobileprovision`, then `base64 -i profile.mobileprovision \| pbcopy` (macOS) or `certutil -encode` (Windows) |
| `TEAM_ID` | Your 10-character Apple Developer Team ID | Apple Developer portal → Membership page |

Base64-encode a file for pasting into a GitHub secret:

```bash
# macOS/Linux
base64 -i MyCert.p12 | pbcopy
```

```powershell
# Windows
[Convert]::ToBase64String([IO.File]::ReadAllBytes("MyCert.p12")) | Set-Clipboard
```

```yaml
name: ios-release-build

on:
  workflow_dispatch:

jobs:
  build:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: "22"

      - run: npm ci
      - run: npm run sync   # regenerates Package.swift with POSIX paths

      - name: Import signing certificate into a temporary keychain
        env:
          BUILD_CERTIFICATE_BASE64: ${{ secrets.BUILD_CERTIFICATE_BASE64 }}
          P12_PASSWORD: ${{ secrets.P12_PASSWORD }}
          KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}
        run: |
          CERT_PATH=$RUNNER_TEMP/build_certificate.p12
          KEYCHAIN_PATH=$RUNNER_TEMP/app-signing.keychain-db

          echo -n "$BUILD_CERTIFICATE_BASE64" | base64 --decode -o $CERT_PATH

          security create-keychain -p "$KEYCHAIN_PASSWORD" $KEYCHAIN_PATH
          security set-keychain-settings -lut 21600 $KEYCHAIN_PATH
          security unlock-keychain -p "$KEYCHAIN_PASSWORD" $KEYCHAIN_PATH

          security import $CERT_PATH -P "$P12_PASSWORD" -A -t cert -f pkcs12 -k $KEYCHAIN_PATH
          security list-keychain -d user -s $KEYCHAIN_PATH
          security set-key-partition-list -S apple-tool:,apple:,codesign: -s -k "$KEYCHAIN_PASSWORD" $KEYCHAIN_PATH

      - name: Install provisioning profile
        env:
          PROVISIONING_PROFILE_BASE64: ${{ secrets.PROVISIONING_PROFILE_BASE64 }}
        run: |
          PROFILE_PATH=$RUNNER_TEMP/profile.mobileprovision
          echo -n "$PROVISIONING_PROFILE_BASE64" | base64 --decode -o $PROFILE_PATH

          mkdir -p ~/Library/MobileDevice/Provisioning\ Profiles
          cp $PROFILE_PATH ~/Library/MobileDevice/Provisioning\ Profiles/

      - name: Archive
        env:
          TEAM_ID: ${{ secrets.TEAM_ID }}
        run: |
          xcodebuild archive \
            -project ios/App/App.xcodeproj \
            -scheme App \
            -configuration Release \
            -archivePath $RUNNER_TEMP/App.xcarchive \
            DEVELOPMENT_TEAM="$TEAM_ID"

      - name: Write ExportOptions.plist
        env:
          TEAM_ID: ${{ secrets.TEAM_ID }}
        run: |
          cat > $RUNNER_TEMP/ExportOptions.plist <<PLIST
          <?xml version="1.0" encoding="UTF-8"?>
          <!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
          <plist version="1.0">
          <dict>
            <key>method</key>
            <string>app-store-connect</string>
            <key>teamID</key>
            <string>${TEAM_ID}</string>
            <key>signingStyle</key>
            <string>automatic</string>
          </dict>
          </plist>
          PLIST

      - name: Export IPA
        run: |
          xcodebuild -exportArchive \
            -archivePath $RUNNER_TEMP/App.xcarchive \
            -exportOptionsPlist $RUNNER_TEMP/ExportOptions.plist \
            -exportPath $RUNNER_TEMP/export

      - uses: actions/upload-artifact@v4
        with:
          name: JLPT-N4-Trainer-ipa
          path: ${{ runner.temp }}/export/*.ipa

      # Optional: push straight to TestFlight instead of (or in addition to)
      # downloading the artifact and uploading it by hand. Needs an
      # App Store Connect API key (three more secrets: key id, issuer id,
      # and the .p8 key content) — see the action's README for setup.
      # - name: Upload to TestFlight
      #   uses: apple-actions/upload-testflight-build@v1
      #   with:
      #     app-path: ${{ runner.temp }}/export/App.ipa
      #     issuer-id: ${{ secrets.APPSTORE_ISSUER_ID }}
      #     api-key-id: ${{ secrets.APPSTORE_API_KEY_ID }}
      #     api-private-key: ${{ secrets.APPSTORE_API_PRIVATE_KEY }}
```

Check `actions/upload-artifact` and `apple-actions/upload-testflight-build` versions before relying on
them — pin to whatever their current major release is at the time you set this up.

Getting the certificate and provisioning profile in the first place is the part that's genuinely
easier with at least brief access to a Mac (Route A or C) — Keychain Access's export flow does in a
few clicks what otherwise takes several `openssl` invocations against a manually-generated CSR. If you
have a friend with a Mac, borrowing it for 20 minutes to generate and export the `.p12` once is likely
less friction than the pure-Windows `openssl` path.

## Route C — rented cloud Mac

Services like [MacStadium](https://www.macstadium.com), [MacinCloud](https://www.macincloud.com),
Scaleway's Mac mini instances, or AWS EC2 Mac instances give you remote-desktop access to a real Mac,
billed hourly or monthly.

**When this beats CI (Route B):** you get an actual interactive Xcode window — useful when a build is
failing in a way that's hard to diagnose from CI logs alone, or when you want to poke around Xcode's
UI (Instruments, the visual Signing & Capabilities editor, interface builder) before scripting anything.

**Its limit:** you cannot plug your own iPhone into a remote machine over the internet. On-device
testing on your actual phone is only possible via Route A. On a rented Mac you're limited to the
Simulator, or shipping a build to TestFlight and installing it on your phone through the TestFlight
app — which does work fine for real-device testing, just not via a USB cable.

Setup is otherwise identical to Route A once you're connected: install Node 22 (Xcode usually comes
preinstalled on these services), `npm ci`, `npm run sync`, open the `.xcodeproj`, sign, build.

## TestFlight & App Store submission

1. **Create the App Store Connect record** at [appstoreconnect.apple.com](https://appstoreconnect.apple.com)
   — My Apps → + → New App. The bundle id must exactly match `com.rgeegallega.jlptn4trainer` (register
   it under Certificates, Identifiers & Profiles first if it isn't already listed).
2. **Bump the version before each new build**: `MARKETING_VERSION` (the user-facing version, e.g.
   `1.1`) and `CURRENT_PROJECT_VERSION` (the build number, must strictly increase per upload) in the
   `App` target's Build Settings, or pass them to `xcodebuild archive` as overrides the way Route B2
   does with `DEVELOPMENT_TEAM`.
3. **Internal vs. external testers**: internal testers (up to 100, must be on your App Store Connect
   team) get builds immediately after processing, no review needed. External testers (up to 10,000)
   require a first build to pass a lightweight Beta App Review.
4. **Export compliance**: App Store Connect asks whether the app uses encryption. This app makes no
   network calls at all (fully offline, no backend, no external APIs) and uses no custom cryptography,
   so answer "No" / select the standard exemption — equivalent to setting
   `ITSAppUsesNonExemptEncryption = false`. You can also add that key directly to
   [`Info.plist`](../ios/App/App/Info.plist) to skip the question on every future upload.
5. **Screenshots**: App Store Connect requires at least one screenshot set for the largest supported
   iPhone size class (6.9" / iPhone 16 Pro Max or equivalent) and, since this app supports iPad
   (`TARGETED_DEVICE_FAMILY = "1,2"`), an iPad set too. Simulator screenshots are accepted.
6. **Privacy nutrition label**: since the app collects no data of any kind (no analytics, no accounts,
   no network calls — progress lives only in on-device `localStorage`), answer "Data Not Collected" for
   every category in the Privacy section.

## Troubleshooting

**SPM package resolution fails / "unable to resolve package"** — you're hitting the backslash blocker
described above. Confirm `path:` values in
[`ios/App/CapApp-SPM/Package.swift`](../ios/App/CapApp-SPM/Package.swift) use forward slashes; if not,
re-run `npm run sync` on the Mac/CI runner, not on Windows.

**"Signing for 'App' requires a development team"** — no team is selected. Xcode: target `App` →
Signing & Capabilities → Team dropdown. CI: pass `DEVELOPMENT_TEAM=<TEAM_ID>` to `xcodebuild`.
`DEVELOPMENT_TEAM` is deliberately left unset in the committed project so this is expected on any new
machine.

**Provisioning profile / bundle identifier mismatch** — the profile you installed doesn't cover
`com.rgeegallega.jlptn4trainer`, or was generated for the wrong certificate type (Development vs.
Distribution). Re-check the bundle id and profile type in the Apple Developer portal.

**"No account for team" / "no signing certificate found"** — your Apple ID isn't signed into Xcode
(Xcode → Settings → Accounts) or your Team ID doesn't match any account signed in on that machine. In
CI this means the imported `.p12` didn't match `TEAM_ID`, or the temporary keychain step failed
silently — check the `security import` step's output.

**Simulator build succeeds, device build fails** — almost always a signing issue, since
`CODE_SIGNING_ALLOWED=NO` sidesteps signing entirely for the simulator but a real device requires a
valid profile + certificate. Revisit the signing steps above.

**Changes made in the code aren't showing up in the app** — the native project bundles a *copy* of the
web build at `ios/App/App/public` (gitignored, listed in `ios/.gitignore`), not a live reference to
`dist/`. Re-run `npm run sync` after any source change before rebuilding in Xcode.

**Orientation looks different between the installed PWA and the native app** — this is a known,
harmless inconsistency, not a bug: the PWA manifest in
[`vite.config.ts`](../vite.config.ts) locks `orientation: "portrait"`, while
[`Info.plist`](../ios/App/App/Info.plist) allows portrait + both landscapes on iPhone (and adds
portrait-upside-down on iPad). If you want them to match, either loosen the manifest's `orientation`
field or restrict `UISupportedInterfaceOrientations` in `Info.plist` — neither has been done yet.
